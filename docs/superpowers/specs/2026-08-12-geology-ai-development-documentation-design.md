# 地礦 AI 系統開發文件包設計規格

- 日期：2026-08-12
- 對象：系統分析師、前端工程師、後端工程師、GIS／GeoServer 工程師與專案管理人員
- 文件性質：工程交接用概念設計，不是既有後端或資料庫的實作規格

## 1. 目標

依據舊系統介面欄位盤點、115 年系統工項規劃及 v15 HTML 雛型，建立一套可供工程團隊估工、拆分模組及確認介面的開發文件包。

文件包需要達成以下目的：

1. 說明三個主要角色可見的功能模組、資料範圍與操作權限。
2. 將雛型畫面對應至後端業務能力、概念資料實體及 GeoServer 圖資需求。
3. 提供概念 ERD，讓工程團隊後續依實際舊資料庫 Schema 完成實體資料模型。
4. 提供技術中立的概念 API 契約，作為前後端及 GIS 介面的討論起點。
5. 依工項規劃原有填色標示工程師 A、B、C 的負責範圍，不重新分配工作。

## 2. 證據來源與使用規則

### 2.1 主要來源

1. `地礦舊系統介面欄位盤點.xlsx`
   - 用於辨識舊系統畫面欄位、查詢條件、輸出欄位及可能的資料內容。
   - 不據此推定舊資料庫的資料表名稱、主鍵、外鍵或實體型別。
2. `115 地礦AI_系統工項規畫 (2).xlsx`
   - 用於確認模組範圍、需求說明、相依事項及原始分工顏色。
3. `地礦AI_雛型_v15_0805_feedback.html` 與目前 GitHub Pages
   - 用於確認介面結構、角色切換、資料範圍、操作流程及畫面欄位。
   - HTML 中的 JavaScript 陣列、函式及範例數字均為假資料，不視為既有 API 或資料庫設計。

### 2.2 證據標籤

所有文件使用以下標籤區分確定程度：

- `已確認`：直接來自 Excel 或 v15 雛型可觀察內容。
- `概念設計`：依業務流程整理的 ERD、API、系統邊界或資料關聯。
- `待工程確認`：必須由工程團隊依舊資料庫、實際技術選型或部署環境確認。

## 3. 文件範圍

### 3.1 納入範圍

- 系統目標與文件閱讀方式
- 邏輯系統架構
- 角色與資料範圍
- 功能模組與主要使用流程
- 舊系統欄位與新系統概念實體的對照
- 概念 ERD
- 概念 API 資源與操作
- GeoServer 與業務資料的概念整合
- 影像、KML、報告及現場照片的附件需求
- 工程師 A、B、C 分工
- 跨模組相依、開發順序及驗收重點
- 技術選型與工程確認清單

### 3.2 排除範圍

- 舊資料庫備份還原
- 舊資料庫 Schema 逆向工程
- 實體資料表、索引、外鍵及 SQL 型別設計
- 資料清理、轉置程式或 Migration Script
- 指定 .NET、資料庫或前端框架版本
- GeoServer Workspace、Store、SLD 及發布腳本的實作細節
- 正式資安設定、網路拓樸或維運手冊
- 將 HTML 雛型中的假資料當成正式資料來源

舊資料沿用只以一項工程依賴呈現：工程團隊須依實際舊資料庫 Schema，將舊欄位對應至本文件的概念實體。

## 4. 目標邏輯架構

文件以技術中立方式呈現以下元件：

1. 前端應用：角色介面、表單、列表、統計儀表板及 GIS 圖台。
2. 後端 API：身分權限、業務流程、查詢、統計、匯出與附件中介。
3. 業務資料庫：保存使用者、點位、範圍、影像期別、查勘、稽催及後續處理資料。
4. 檔案儲存：保存影像、KML、判釋報告、現場照片及輸出成果。
5. GeoServer：發布底圖以外的專案圖層、點位、範圍及影像相關圖資。
6. AI 判釋來源：提供建議監測點位或判釋成果，由後端匯入業務流程。

文件只規定元件責任與資料流，不指定技術版本。

## 5. 角色設計

正式角色矩陣以三個角色為主：

### 5.1 地礦中心承辦

- 資料範圍：當年度全台或其被授權的專案範圍。
- 主要能力：選定監測範圍、確認拍攝、通報地方政府、查看查勘回報、稽催、查看違規後續處理、統計分析及使用者管理。
- 權限限制：依雛型，不顯示僅供空拍廠商使用的手動新增監測範圍與建議拍攝點位操作。

### 5.2 地方政府人員

- 資料範圍：帳號被授權的縣市。
- 主要能力：查看轄區變異點、填寫查勘回報、上傳現場照片、填寫處分或移交後續資訊、查看自身轄區通知與狀態。
- 權限限制：不可查看或操作其他縣市資料；系統管理及全台統計依雛型權限限制處理。

### 5.3 系統管理員

- 資料範圍：全系統。
- 主要能力：帳號開通與註銷、角色與容許瀏覽縣市設定、系統日誌，以及必要的系統級查詢。
- 權限設計原則：系統管理權限與一般業務操作權限分開描述；是否同時擁有業務角色由實作時確認。

### 5.4 空拍廠商

雛型包含空拍廠商角色及專屬操作，因此文件保留為「外部協作角色／待確認角色」。其畫面可作為空拍資料上傳與點位新增流程的需求證據，但不併入使用者指定的三個正式角色矩陣。

## 6. 概念 ERD 範圍

概念 ERD 以業務領域分組，不使用實體資料表名稱：

### 6.1 帳號與授權

- 使用者
- 角色
- 使用者角色
- 縣市
- 使用者容許瀏覽縣市
- 操作日誌

### 6.2 專案與監測位置

- 監測專案／專案年度
- 建議監測點位
- 監測範圍
- 監測點位
- 地籍位置
- 監測方式

### 6.3 影像與判釋

- 影像期別
- 影像資料
- 判釋成果
- GeoServer 圖層參照
- 附件

### 6.4 通報、查勘與回報

- 變異點案件
- 通報查勘
- 查勘回報
- 現場照片
- 違規類型／違反法規

### 6.5 稽催與後續處理

- 稽催案件
- 稽催紀錄
- 稽催設定／通知範本
- 違規後續處理
- 移交紀錄

主要關聯方向為：專案產生監測位置；監測位置具有影像期別與判釋成果；判釋成果形成變異點案件；案件經通報後產生查勘回報；逾期案件產生稽催紀錄；確認違規後產生後續處理與移交紀錄。

## 7. 概念 API 文件設計

API 文件為單檔 HTML，定位為前後端溝通用候選契約。

### 7.1 文件章節

- API 文件定位與非實作聲明
- 身分與角色授權原則
- 共通資料格式、分頁、查詢條件與錯誤格式
- 各模組候選資源與操作
- 角色／端點權限矩陣
- GeoServer 整合責任邊界
- 附件上傳與下載需求
- 欄位來源標籤
- 待工程確認事項

### 7.2 候選 API 領域

- Auth／Current User
- Users／Roles／Allowed Counties
- Projects
- Suggested Monitoring Points
- Monitoring Areas／Monitoring Points
- Imagery／Interpretation Results／Attachments
- Investigation Cases／Notifications／Survey Reports
- Reminders／Reminder History／Reminder Settings
- Violations／Transfers／Dispositions
- Statistics／Exports
- GIS Layers／Feature References
- Audit Logs

候選路徑可使用 `/api/v1/...` 方便閱讀，但必須標示為概念命名，工程團隊可依既有標準調整。

## 8. 工程分工標示

工項規劃的填色只轉換為代號，不變更原有工作範圍：

- 工程師 A：藍色系區塊，包含登入／註冊、首頁及系統管理相關工作。
- 工程師 B：綠色區塊，包含圖台、稽催及統計分析相關工作。
- 工程師 C：黃色區塊，包含監測位置、查勘回報及違規後續處理相關工作。
- AI 訓練粉紅色區塊：保留工項表原有負責人，不改標成 A、B 或 C。

若同一模組涉及多色工作，文件分別標示主責與介面相依，不自行合併分工。

## 9. 交付成果

### 9.1 Markdown 開發文件

- 適合上傳 GitHub 閱讀與版本控管。
- Mermaid 呈現邏輯架構、概念 ERD 及主要流程。
- 使用相對路徑引用必要截圖。

### 9.2 Word 開發文件

- 與 Markdown 內容一致，排版適合會議審閱與正式交付。
- 使用標題階層、目錄、表格、流程圖及概念 ERD。
- 不把大段一般說明塞入表格。

### 9.3 工程師說明簡報

- 預計 12 至 15 頁。
- 內容順序：系統定位、證據邊界、邏輯架構、角色矩陣、主流程、雛型畫面、概念 ERD、API 邊界、GeoServer 整合、工程分工、相依關係及待確認事項。
- 使用實際 v15 雛型畫面，但清楚註明畫面資料為假資料。

### 9.4 單檔 HTML API 文件

- 可直接以瀏覽器開啟。
- 具章節導覽、搜尋或模組篩選、角色標籤、Request／Response 範例及欄位來源說明。
- 不依賴本機絕對路徑或後端服務即可閱讀。

## 10. 視覺與文字設計

- 語言：繁體中文；API 資源與 JSON 欄位使用一致英文命名。
- 風格：政府專案工程交接文件，資訊密度高但可快速掃讀。
- 主色：延續雛型的地礦綠，搭配深藍灰與單一警示色。
- 截圖：只作為畫面／流程證據，不作為後端完成證據。
- 所有圖表均附圖名、來源或證據標籤。

## 11. 驗證方式

### 11.1 內容驗證

- 每個角色權限可追溯至雛型顯示邏輯或工項規劃。
- 舊系統欄位只使用試算表中實際記錄的內容。
- 概念 ERD 不出現未有業務依據的核心實體。
- API 文件不聲稱後端端點、資料表或驗證機制已經存在。
- 三份主要文件的術語、角色、模組與分工一致。

### 11.2 Artifact 驗證

- Markdown：檢查連結、Mermaid 語法與 GitHub 可讀性。
- Word：渲染每一頁為 PNG，逐頁檢查裁切、表格、字型及分頁。
- PowerPoint：渲染全部投影片，檢查文字溢出、圖片比例及頁碼。
- HTML：以瀏覽器檢查導覽、響應式版面、程式碼區塊及所有模組章節。

## 12. 成功條件

1. 工程師能從文件辨識模組邊界、主責人與介面相依。
2. 前後端能依概念 API 開始討論 Request／Response，而不誤認為既有契約。
3. 工程團隊能以概念 ERD 對照實際舊資料庫 Schema，完成後續實體設計。
4. 三個正式角色的資料範圍與操作權限沒有互相矛盾。
5. HTML 雛型的假資料及實際目標架構被清楚區隔。
