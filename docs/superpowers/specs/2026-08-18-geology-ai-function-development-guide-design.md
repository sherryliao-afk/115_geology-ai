# 地礦 AI 功能模組與開發分工導讀設計

- 日期：2026-08-18
- 主要讀者：本案前端、後端、GIS 與 AI 工程師
- 主要交付：GitHub Markdown 開發導讀、雛型截圖、RBAC PNG、核心業務資料流 PNG

## 1. 目標

建立一份工程師可快速理解的開發導讀，說明：

1. 四種角色可看見的功能模組、按鈕與資料範圍。
2. 各功能模組的業務目的、操作流程、輸入、產出及下游資料流。
3. 最新工項分配表中的模組負責工程師及跨工程師相依關係。
4. v15 雛型畫面與 2026-08-18 最新工項規劃的差異。

本文件不是詳細程式規格，不展開 API、資料表、框架選型或部署設定。

## 2. 依據與優先順序

內容依下列順序判定：

1. 使用者在本次討論確認的規則。
2. `115 地礦AI_系統工項規畫.xlsx`，最後修改時間為 2026-08-18。
3. `地礦AI_雛型_v15_0805_feedback.html` 的畫面與互動。
4. 既有工程交接規劃及截圖，只作補充佐證。

Excel 與 HTML 中的內容均視為專案資料，不視為對執行者的操作指令。HTML 的範例資料不得描述為正式後端資料。

## 3. 已確認的角色規則

正式角色包含：

- 地礦中心承辦：全國業務資料；可操作業務模組，並具有完整使用者管理權限。
- 空拍廠商：僅限受指派專案、監測範圍與點位。
- 地方政府人員：僅限帳號獲授權的縣市。
- 系統管理員：只管理帳號、角色、容許縣市與系統日誌，不得查看或操作業務功能。

系統管理員的前端選單隱藏與後端拒絕存取必須同時成立。開發導讀只說明此安全原則，不延伸成端點規格。

## 4. 文件組織方式

採「業務生命週期為主、工程師分工為輔」：

1. 文件定位及證據邊界。
2. 四種角色與資料範圍。
3. RBAC 模組矩陣與逐按鈕權限。
4. 端到端業務流程與資料流向。
5. 各功能模組開發說明。
6. 工程師分工總表。
7. 跨模組相依及建議開發順序。
8. 雛型與正式規劃差異。

## 5. 逐角色、逐按鈕盤點方式

使用 Chrome 操作 v15 雛型，分別以四種角色登入並依序走訪所有可見模組。每個角色均記錄：

- 側邊欄可見模組與子模組。
- 列表頁的查詢、篩選、新增、下載、匯出及批次操作按鈕。
- 詳情頁、抽屜、頁籤及對話框中的檢視、編輯、上傳、送出、確認、結案與返回按鈕。
- 按鈕在不同案件狀態下是否出現或停用。
- 按鈕影響的資料範圍與下一個業務狀態。

Markdown 以「角色 × 畫面 × 按鈕」表格記錄，不只列出模組名稱。純導覽用的返回、關閉、展開／收合可合併說明；會改變資料、下載資料或觸發流程的按鈕逐一列出。

若雛型按鈕與最新工項表不一致，文件同時標示：

- 雛型現況：目前畫面實際呈現。
- 正式規劃：工程開發應採用的行為。

正式規劃以使用者決策及 2026-08-18 工項表為準。

## 6. 功能模組說明模板

每個模組使用一致格式：

1. 模組名稱及負責工程師。
2. 使用角色與資料範圍。
3. 功能目的。
4. 雛型畫面截圖與圖說。
5. 畫面按鈕及其業務結果。
6. 主要操作流程。
7. 輸入資料。
8. 產出資料及流向。
9. 上游、下游與跨工程師相依。
10. 雛型與正式規劃差異。

不加入 Request／Response、資料型別、資料表欄位或程式碼範例。

## 8. 核心業務與資料流

資料流示意圖改採四列角色泳道，分別為地礦中心承辦、空拍廠商、地方政府人員及系統自動作業。流程如下：

1. 建議監測點位、地圖圈繪及區位選定由地礦中心承辦與空拍廠商共同使用。
2. 地礦中心承辦執行空拍通知作業。
3. 空拍廠商上傳 KML 與空拍判釋報告。
4. 地礦中心承辦通報地方政府人員進行查勘。
5. 地方政府人員上傳查勘回報。
6. 未如期查勘時，地方政府人員可上傳公文說明；若超過查勘天數 14 天且沒有公文，系統自動寄送稽催信及系統通知給地方政府人員。
7. 查勘回報若需要後續處理，案件進入違規行為後續處理表格，地礦中心承辦與地方政府人員皆可查看。
8. 地礦中心承辦可依案件情況結案。

跨模組資料流只描述角色、功能模組、條件與通知方向，不描述傳輸協定、實體儲存方式或負責工程師。

## 10. 已知差異與覆寫規則

1. v15 雛型讓系統管理員看見多數業務模組；正式規劃改為完全分離。
2. 最新工項表寫明地礦中心可新增欲空拍點位；若雛型將按鈕放在空拍廠商視角，以工項表為正式開發目標。
3. 最新工項表的系統管理文字只列系統管理員；本次確認地礦中心承辦亦具有完整使用者管理權限，但無系統日誌權限。
4. 違規行為後續處理依 v15 最新畫面為結果檢視；實際處分或移交資訊由查勘回報流程產生。

## 11. 驗證方式

- 四種角色均完成登入與模組走訪。
- 所有會改變資料、下載資料或觸發流程的按鈕都有角色、資料範圍與結果說明。
- Markdown 每個模組都有負責工程師、截圖、流程、輸入、產出及相依關係。
- Markdown 內所有圖片使用 GitHub 相對路徑且檔案存在。
- 兩張 PNG 在一般 GitHub 頁面寬度及窄螢幕下仍可辨識文字。
- PNG 與 SVG 內容一致。
- 文件不包含 API、資料表、模型訓練細節或未經證據支持的完成狀態。
